# Documentation Site Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the hand-built `site/` with a Starlight documentation site, served at `https://maxkuttner.github.io/openoms/`, that takes a trader from nothing to a filled paper order and an authenticated API call.

**Architecture:** A self-contained Astro + Starlight project in a new top-level `docs-site/`. Markdown/MDX pages under `docs-site/src/content/docs/`. The API reference is generated at build time from the committed `docs/openapi.json` by `starlight-openapi`. `install.sh` is copied in at build time. A `node --test` suite runs against the built `dist/` and the sources to catch the failure modes in Review Focus. `pages.yml` builds `docs-site/` instead of assembling `site/`.

**Tech Stack:** Node 22, Astro 5, `@astrojs/starlight`, `starlight-openapi`, `starlight-links-validator`, a Mermaid renderer (builder's choice, see Task 3), `node:test`.

**Spec:** `docs/superpowers/specs/2026-10-29-docs-site-design.md`

## Global Constraints

- Site served at `https://maxkuttner.github.io/openoms/`; Astro `site: "https://maxkuttner.github.io"`, `base: "/openoms"`. Every link and asset works under `/openoms/`.
- `https://maxkuttner.github.io/openoms/install.sh` serves the repo's `install.sh` byte-identical. The repo copy stays canonical; never commit a second copy.
- API reference generated from `docs/openapi.json` only. No hand-written endpoint reference pages.
- Docs match `main`: config search order `$OMS_CONFIG` → `./oms.toml` → `~/.config/oms/oms.toml` (or `$XDG_CONFIG_HOME/oms/oms.toml`) → `/etc/oms/oms.toml`; `oms init` writes the per-user location; `.env` beside the config is loaded after `./.env`; `oms update [--check] [--version vX.Y.Z]`.
- Supported install platforms: exactly `aarch64-apple-darwin` and `x86_64-unknown-linux-gnu` (glibc ≥ Ubuntu 22.04 / Debian 12, OpenSSL 3). Everything else: "build from source".
- Python client install line, verbatim: `pip install "git+https://github.com/maxkuttner/openoms#subdirectory=clients/python"`.
- `deploy/` is not mentioned in the public docs. "Running as a service" = hand-written systemd unit; state plainly that no Docker image is published yet.
- State real gaps where a reader would hit them (no equity price feed, no systemd installer, no published Docker image). Never document a feature that does not exist.
- First paper trade: 1 share of AAPL on Alpaca paper.
- No analytics, tracking, hosted services or paid dependencies.
- Pin exact dependency versions in `docs-site/package.json` (no `^`); commit `package-lock.json`.

## Review Focus

1. **A link or asset that works at `/` but breaks under `/openoms/`** — a reader clicking any internal link or loading any image lands on a real page. → Task 1 `every internal href in dist resolves to a built file`.
2. **`install.sh` missing, altered, or served as HTML** — `curl -fsSL …/install.sh | sh` keeps working after the switch. → Task 1 `install.sh in dist is byte-identical to the repo copy`.
3. **Docs naming an `oms` command or flag that does not exist** — a copied command runs. → Task 4 `every oms command in the docs is a real subcommand`.
4. **An endpoint missing from the API reference** (e.g. the spec grows and the plugin silently skips an operation) — the trading endpoints a reader needs are there. → Task 2 `the API reference has a page for each trading endpoint`.
5. **Diagrams unreadable in one colour scheme** — architecture diagrams render in both light and dark mode. → Task 3 manual check step (visual; no automated assertion is worth its cost).
