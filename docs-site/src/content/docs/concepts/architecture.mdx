The central OMS is one program. Its core owns durable accounting state in
Postgres. Two embedded gateways connect it to venues: one for orders and fills,
one for prices. Co-located strategies are separate programs with direct venue
connections and an asynchronous control link to the OMS.

This illustration shows the existing implementation. The proposed embedded
runtime is shown separately under [Target architecture](#target-architecture).

## The order path

1. An order arrives from the cockpit, the trader UI, or a strategy over FIX or
   REST (path ①).
2. **Order API + Risk** checks it against the portfolio's limits and current
   positions, then stores it.
3. The **order gateway** sends it to the venue through that venue's connector.
4. The venue's executions come back through the same connector as plain
   `ExecEvent`s.
5. The **order engine** applies them. It is the only place that books a fill,
   and it books each fill once, however often it is reported.
6. Every change is appended to the **event store**, then published on the event
   bus.

**Order recon** asks the gateway for open orders and order status after every
reconnect, and lets the order engine heal anything missed while a stream was
down.

## The price path

- The **market data gateway** subscribes to the instruments the OMS holds, on
  the crypto venues' public feeds and on OPRA for options.
- It turns each venue's messages into one shared quote.
- **Pricing** keeps the best live source per instrument and fails over when it
  goes stale.

Prices never wait for orders and orders never wait for prices: the two paths
share no queue.

## The event bus

The bus is in memory and has two lanes:

| Lane | Carries | Guarantee |
|---|---|---|
| Order lane | order events, fills, position changes | published only after the event is stored; a subscriber that falls behind re-reads the event store |
| Price lane | marks | latest value wins; a slow subscriber skips ahead and slows nothing |

Positions & P&L, UI updates (one WebSocket to every open screen) and the
strategy reports subscribe to it. The **Kafka outbox** reads the event store
rather than the bus, so other systems catch up after an outage. Kafka is
optional; without it the OMS runs fully.

## Strategies

- **Path ①, through the OMS.** The strategy sends its orders to the OMS over
  FIX 4.4 (TLS) or REST, and every order passes the same checks as a trader's.
  See [FIX](/openoms/strategies/fix/) and [REST](/openoms/strategies/rest/).
- **Path ②, co-located.** A latency-sensitive strategy runs on its own server
  next to the venue and trades its own venue account directly. It links four
  crates from this repository:
  - `risk` is the shared pure pre-trade evaluator;
  - `colo-runtime` owns reservations, the durable journal and recovery;
  - `colo-link` holds two authenticated v2 sockets — control and events;
  - `gateway` provides the venue connector.
  The v2 event socket cannot authorize trading; authority arrives only on the
  control socket and is valid from receipt time.

  The OMS follows that account with its own key and books every fill, so the
  strategy's positions and P&L appear moments later. Kill tells the strategy,
  and also cancels everything on the account with the OMS's key, without
  waiting for the strategy. See [Co-located strategies](/openoms/strategies/colocated/).

## Target architecture

**Proposed design, not implemented.** Path ② evolves into a strategy linked with
an embedded execution runtime. It is one process: strategy calls runtime, runtime
checks and reserves exposure, then calls the venue adapter. There is no internal
REST/IPC hop and no per-order OMS or database round trip. Venue protocol latency
and proposed local durable journal writes still contribute to admission latency.

<ArchitectureDiagram target />

### State and responsibility

| Component | Target responsibility |
|---|---|
| Shared `risk` crate | Consistent units, effective-policy rules, directional exposure, strict Reducing and rejection reasons for both paths |
| Embedded runtime (proposed `colo-runtime`) | Atomic admission and reservations, order lifecycle, immediate positions, rate counters, journal and recovery |
| `gateway` crate | Venue execution reports, order/query operations and market data; linked into the same process |
| `colo-link` | Authenticated bootstrap, versioned policy/control, authority, acknowledgements and replayable events |
| Central OMS | Policy and bounded allocations, consolidated accounting, monitoring and independent venue reconciliation |

The proposed initial scope is **trusted strategies, one active runtime per dedicated venue
account/subaccount**, with Binance Spot as the first proposed adapter target.
Sharing an account or global allocation across independent runtimes requires
additional coordination; copying the same global limit to each process is unsafe.

### Configuration is cached; execution state is maintained

On startup, the OMS supplies a versioned snapshot of instruments, permissions,
effective limits, account identity and execution settings. The runtime installs
updates atomically and acknowledges their exact version. Secrets are provisioned
separately from ordinary configuration and event logs.

Local positions, pending/working orders and reservations advance from venue events
immediately. A partial fill moves exposure from working quantity to position in
one transition. A timeout remains an unknown commitment, and requesting a cancel
does not release capacity. Opposing working orders do not simply net to zero.
Spot orders also reserve shared quote/base assets across instruments, including
fee allowances; separate symbol limits must not spend the same balance twice.

The runtime reconciles its journal and OMS baseline against venue orders and fills
before enabling trading. An OMS position snapshot cannot overwrite newer local
fills without a matching checkpoint. Errors or missing history must not become an
empty account. The OMS order path retains transactional admission while reusing
the same risk evaluator with a coherent database exposure snapshot.

### Asynchronous supervision and accounting

OMS-to-runtime traffic carries bootstrap, policy, bounded authority and commands.
Runtime-to-OMS traffic carries submissions, execution reports (including fills),
health and acknowledgements. Events have stable identities and sequences, survive
reconnect through replay, and are acknowledged after durable acceptance. The OMS
deduplicates runtime reports against its independent venue-follow stream so one
economic fill is booked once.

On authority expiry, the runtime stops new risk and attempts cancellation; unknown
orders and existing positions remain charged. A replacement cannot start spending
the allocation until the previous owner is stopped and recovery completes.
In-process checks are cooperative controls for trusted code, not an independent
security boundary. Neither a kill command nor an in-process watchdog guarantees
that a crashed or bypassing strategy's orders disappear within a fixed deadline.
Venue-native protections must be verified for the specific API and product.
Suspended or expired runtimes permit cancellation/recovery only. Kill remains
latched across restart until an explicit newer Enable command and successful
recovery authorize resumption; ordinary policy updates do not clear it.

### Changes from the shipped design

1. Shared `risk` semantics are extracted from the OMS checks and the legacy
   co-located risk book, with valuation, working exposure and Reducing explicit.
2. Move ad hoc strategy execution into the embedded runtime with reservations,
   a recoverable journal and locally maintained positions.
3. Extend the control link to full bootstrap/policy and replayable event contracts.
4. Preserve independent OMS venue follow, adding cross-source event deduplication.
5. Verify restart, disconnect, unknown-order and concurrent-admission behavior,
   and measure tail latency before rollout.

The detailed design is in repository file
`docs/superpowers/specs/2026-11-07-colocated-runtime-design.md`. Initial venue/account
scope, opening-inventory accounting, authority/freshness defaults and the
durable-before-send latency budget require review before implementation.

## Instrument model

One canonical instrument catalog sits in the middle, with two independent
mappings off it: a broker's tradable handle (`broker_instrument`, a table) and a
data feed's pricing symbol (`FeedSymbology`, derived in code). Whether an
instrument can be **priced** and whether it can be **traded** are independent.

| | What it is |
|---|---|
| **Master** — `instrument` | Canonical identity, keyed `(symbol, venue)`. Asset and instrument class, microstructure, FIGI. Option legs live in `instrument_derivative`. |
| **Execution** — `broker_instrument` | The tradable mapping: one row per instrument per broker, with `broker_symbol`, `native_id` and limits. Written by `oms setup sync-broker` from the broker adapter's instrument list. A row existing means the instrument is tradable through that broker. |
| **Market data** — `FeedSymbology` | The pricing mapping, one-to-many — and a pure function, not a table. `candidates()` picks the slice of the catalog a feed covers; `to_feed_symbol()` renames each hit into the feed's own symbol. One symbol can price the same pair on several venues. Evaluated at subscribe time. |

## End to end

One catalog in the middle, an adapter at each end. **Brokers write it:**
`sync-broker` asks each broker what it lists and stores that as an `instrument`
plus a `broker_instrument` routing row. **Feeds only read it:** at subscribe
time, `FeedSymbology.candidates()` picks the slice of the catalog that feed
covers and `to_feed_symbol()` renames each instrument into whatever that feed
calls it.

That second mapping is computed, not stored — there is no feed table anywhere.
It is rebuilt from the catalog on every subscription, which is why a broker
sync that adds instruments needs no follow-up step to make them priceable, and
why nothing can go stale. Each adapter owns its own symbology, so neither end
knows the other exists.

## Tables and relationships

Foreign keys are shown. `broker_instrument` references the master
`instrument`. There is no feed table: the pricing mapping is derived in code.
Two links are soft, by code rather than foreign key: `broker_code` →
`broker_connection`, and `feed_code`, which is ranked for failover in
`provider_feed_policy`.

## Runtime — the two paths

Pricing derives its symbols through `FeedSymbology`; order routing reads
`broker_instrument`. The two never cross — a feed can price an instrument no
broker trades, and a broker can trade an instrument no feed prices.
